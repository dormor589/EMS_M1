### What to build

#### 1. `docs/explanation.txt` (plain text)

Use brief §14 template verbatim as the structure. Populate with the ACTUAL state of the codebase as of D007 PASS:

Sections:
- Project Name + Milestone
- Project Goal
- Users (Teacher, Student, optional Admin future)
- Teacher Use Cases (list of actually-implemented features)
- Student Use Cases (list of actually-implemented features)
- Implemented in Milestone 1: enumerate (React structure, mock auth, role-based nav, services, mock DB, etc.)
- Not Implemented Yet: real backend, Postgres, JWT, deployment, real-time, AI, analytics
- Main Services: list all 8 with one-line responsibility
- Main Entities: list 5 entities with one-line description
- How to Run: 3-step instructions for client + server
- Known Limitations: mock auth (passwords plain text in localStorage), no real backend, etc.

Strict format: **plain text, no Markdown syntax** (no `#`, `**`, code fences). Use simple ASCII headers / dashes for visual structure.

If anything diverges from this in the actual code, document the divergence (do NOT modify the code to fit — modify the diagram to reflect reality).

#### 3. `docs/diagrams/use-case-diagram.puml`

Use brief §15.2 as the starter; refine to reflect what's actually implemented. PlantUML syntax `@startuml ... @enduml`. Include both actors (Teacher, Student) and all M1 use cases.

#### 4. `docs/diagrams/class-diagram.puml`

Use brief §15.3 as the starter. Include:
- Entity classes: User, Exam, Question, Submission, Answer
- Service classes: ConfigService, LoggerService, StorageService, NotifyService, MockApiService, AuthService, ExamService, SubmissionService
- Relationships: User creates Exam (1:N), Exam contains Question (1:N), User submits Submission (1:N), Exam receives Submission (1:N), Submission embeds Answer (1:N)
- Show key attributes per class
- Show key methods per service class

### Required commit structure (BINDING — docs split from impl)

D008 is docs-only; commit each artifact (or logically grouped pair) separately:

1. `docs: add explanation.txt with project overview and use cases`
2. `docs: add component-hierarchy diagram`
3. `docs: add class-diagram (PlantUML)`
4. `docs: add use-case-diagram (PlantUML)`
5. `docs: add entities reference`
6. `docs: append D008 entry to ai-work-log`

(If you co-commit two related diagrams in one commit, that's fine — but minimum 4 distinct `docs:` commits.)

After last commit: `git push origin dev`.

### Acceptance criteria

- [ ] All 5 documentation artifacts exist under `docs/`.
- [ ] `explanation.txt` is plain text (no Markdown syntax).
- [ ] Diagrams reflect ACTUAL code, not the brief's template verbatim where the code diverges.
- [ ] PlantUML files compile (no need to render — just valid `@startuml`/`@enduml` syntax + valid class/use-case body).
- [ ] ai-work-log entry added.
- [ ] ≥4 `docs:` conventional commits on dev; pushed.

### Out of scope

- Visual / rendered diagram images (PNG/SVG) — source files only in M1.
- Optional sequence/activity diagrams (M2 nice-to-have).

### Failure modes

- explanation.txt accidentally Markdown — re-author in plain text.
- Diagrams describe planned features rather than implemented — review actual code first, document reality.

### Deliverable

- 5 docs/diagrams files, ai-work-log update.
